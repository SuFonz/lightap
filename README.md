# LightAP

A lightweight **ActivityPub** community implementation — think of it as "building your own little corner of the Fediverse by hand on Cloudflare Workers."

LightAP implements the core pieces of ActivityPub (WebFinger, Actor, Inbox / Outbox, HTTP Signatures), so users on this instance can follow and exchange posts with Fediverse software such as Mastodon and Misskey. The frontend is a friendly community UI with a public timeline, a following timeline, posting, following users, and user search.

> The name comes from **Light** (lightweight) + **AP** (ActivityPub).

## Features

- 🌐 **Federation protocol support**
  - WebFinger (`/.well-known/webfinger`)
  - Actor documents (`/users/:username`)
  - Inbox / Outbox (`/users/:username/inbox`, `/users/:username/outbox`)
  - Signed delivery via HTTP Signatures, compatible with both the legacy `Signature` header and **RFC 9421**
  - Sending and receiving `Create`, `Follow`, `Undo`, `Accept`, and other activities
- 📝 **Community features**
  - User registration / login (JWT + cookie session)
  - Posting, public timeline, following timeline
  - Follow / unfollow, including searching for and following remote Fediverse users
  - User profiles, post detail pages, notifications
  - Local user search plus remote user discovery via WebFinger
- 🎨 **UI**: Tailwind CSS glassmorphism styling, responsive layout, mobile navigation
- ⚡ **Serverless**: deployed on Cloudflare Workers, with D1 as the database

## Getting Started

### Prerequisites

- [Node.js](https://nodejs.org/) (20+ recommended)
- [Cloudflare Wrangler](https://developers.cloudflare.com/workers/wrangler/) (installed as a devDependency; `npx wrangler` also works)

### 1. Install dependencies

```bash
npm install
```

### 2. Configure environment variables

Create a `.dev.vars` file in the project root (for local development):

```dotenv
JWT_SECRET=replace-with-your-own-random-secret
```

> For production, configure it with `wrangler secret put JWT_SECRET` and never commit it to the repository.

### 3. Configure the D1 database

In `wrangler.jsonc`, replace `d1_databases[0].database_id` with your own D1 database ID. You can create one with:

```bash
npx wrangler d1 create lightap
```

### 4. Initialize the database and start the dev server

```bash
npm run dev
```

`npm run dev` initializes the local D1 database from `lightap.sql`, then starts the vinext dev server.

## Federation (ActivityPub) Endpoints

| Endpoint | Description |
| --- | --- |
| `GET /.well-known/webfinger?resource=acct:user@host` | WebFinger lookup |
| `GET /users/:username` | Returns the Actor (`application/activity+json`) |
| `GET /users/:username/outbox` | Public Outbox collection |
| `POST /users/:username/outbox` | Local user posts an activity (requires `Authorization: Bearer <JWT>`) |
| `GET /users/:username/inbox` | Inbox collection (requires auth) |
| `POST /users/:username/inbox` | Receives activities delivered by remote instances |
| `GET /users/:username/followers` | Followers collection |
| `GET /users/:username/following` | Following collection |

| `GET` | `/api/v1/search?q=` | Search local users or remote users (`@user@domain`) |

## Database Schema

The schema is defined in [`lightap.sql`](./lightap.sql) and mainly includes:

- `users`: local and remote users; stores Actor URLs, profile data, password hashes, and RSA key pairs
- `objects`: posts (Notes) and similar objects
- `activities`: records of received activities
- `follows`: follow relationships
- `timeline`: timeline delivery table (recipient relationships for original and reposted posts)
- (OAuth-related tables are reserved but currently commented out)

## Deploying to Cloudflare

1. Edit `wrangler.jsonc` and fill in your `database_id` and other settings.
2. Configure the production secret: `npx wrangler secret put JWT_SECRET`
3. Initialize the remote D1 database: `npx wrangler d1 execute lightap --remote --file ./lightap.sql`
4. Deploy: `npm run deploy`

## Status and Known Limitations

Because the project is in Alpha and most of the code was generated by AI, it currently has the following limitations (a non-exhaustive list):

- Full ActivityPub coverage is not implemented yet; for example, sending/receiving `Delete`, `Like`, and `Announce` (boost) is incomplete
- Parts of the timeline / notifications / likes features are still placeholders
- Once written, objects in `objects` cannot be edited or deleted
- Security and performance have not been systematically audited or optimized
- The frontend relies on several client-side stores, so SSR and hydration consistency still need refinement
